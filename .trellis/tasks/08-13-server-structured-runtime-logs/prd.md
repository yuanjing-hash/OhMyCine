# Server 结构化运行日志与日志中心

## Goal

为 OhMyCine Server 建立可长期运维的结构化运行日志系统，让管理员能在 Web 管理端按模块、组件、插件和业务关联对象精确检索问题，同时保证本地日志文件自动切割、压缩、保留和清理，并且不会泄露凭据、Server 绝对路径或可复用的云端直链。

## Background

- Server 当前使用 zerolog 输出到 stdout；生产环境输出 JSON，开发环境输出 ConsoleWriter。
- Server 已有独立的 SQLite `audit_logs` 与 `audit.read` 权限，但没有运行日志持久化、查询 API、轮转、压缩或保留机制。
- Web 管理端顶栏已有“日志中心”入口，其中审计日志已存在，运行日志仍是规划状态。
- 运行日志用于诊断服务和媒体流水线；审计日志用于记录安全与配置变更。两者必须分域、独立授权、独立保留，运行日志清理不得删除审计记录。

## Requirements

### 1. 统一结构化日志契约

- Server 代码通过统一 Logger 工厂或作用域 Logger 写日志，继续使用 zerolog，不允许业务模块自行建立不受控的文件日志。
- 每条运行日志至少包含时间、级别、消息、`module` 与 `component`。
- 在上下文存在时使用稳定关联字段：`request_id`、`user_id`、`task_id`、`library_id`、`connection_id`、`storage_id`、`downloader_id`、`scan_run_id`。
- 插件日志使用受宿主注入并绑定的 `plugin_id`；插件不得声明或伪造其他插件的标识。
- 支持 `debug`、`info`、`warn`、`error` 级别；默认生产级别可配置，级别变更不要求重启的能力可在设计阶段评估。

### 2. 输出、轮转与故障降级

- 默认同时输出到 stdout 和 Server 本地运行日志目录，便于 Windows 本地运行、NAS、systemd 与容器采集。
- 日志目录必须可通过 Server 配置覆盖；默认位于 Git 忽略的运行时目录中，不得写入源码目录中的可提交文件。
- 活跃日志按单文件大小切割，历史分片使用 gzip 自动压缩。
- 按保留天数、历史分片数量和总容量三重约束清理，达到任一限制时从最旧分片开始删除。
- 默认策略为单文件 20 MiB、最多 10 个 gzip 历史分片、保留 30 天、运行日志总量不超过 500 MiB；任一条件先满足即清理最旧分片。
- Server 启动时执行一次保留清理，运行期间定期清理；异常退出后重启仍能识别并管理遗留分片。
- 文件日志初始化、写入、轮转、压缩或清理失败时，Server 继续保留 stdout 输出并报告安全的降级错误，不因日志子系统故障退出或递归产生日志风暴。
- 多线程并发写入、Windows 文件占用、重命名失败和磁盘空间不足必须有确定行为。

### 3. 脱敏和隐私边界

- 统一脱敏层必须覆盖 Authorization、Cookie、API key、token、passkey、JWT、密码、115/OpenList/Alist/CloudDrive2 凭据、AI key、签名代理参数以及包含凭据的上游 CDN URL。
- HTTP 请求日志只记录规范化路由，不记录可能携带签名或凭据的原始 query string 和请求/响应正文。
- 媒体、存储和扫描日志默认记录 provider-relative path 或资源 ID，不记录 Server 本地绝对路径；必要诊断信息以安全摘要表达。
- API 查询、Web UI 展示和日志导出必须读取同一份已脱敏内容，不能仅在前端遮盖敏感值。
- 日志字段应设置长度和集合数量上限，避免外部错误正文、插件或高基数字段造成磁盘滥用。

### 4. 查询 API 与权限

- 新增稳定权限 `logs.read`、`logs.export` 和 `logs.configure`，分别控制运行日志查询、导出和策略修改；现有审计日志继续使用 `audit.read`，这些权限互不隐含。
- 查询接口使用 `/api/v1/`、标准响应 envelope、分页/游标以及强制时间范围与结果上限。
- 支持组合筛选：时间范围、级别、模块、组件、插件、关键字，以及存在时的各关联 ID。
- 提供可筛选值接口或聚合信息，使前端无需硬编码未来模块和已安装插件列表。
- 关键字查询必须有长度、字符处理、超时和扫描范围限制，不能把任意日志目录变成文件读取接口。
- 查询响应和导出响应使用 `Cache-Control: no-store`；权限拒绝与查询行为不得泄露日志目录、文件名或 Server 绝对路径。
- MVP 查询历史轮转文件；实时追尾/流式订阅不作为本任务的必要条件，除非后续产品决定纳入。

### 5. Web 日志中心

- 顶栏“日志中心”保留为统一入口，包含“运行日志”和现有“审计日志”两个独立子页，不增加侧栏一级导航。
- 运行日志页面支持时间、级别、模块、组件、插件、关键字和业务关联 ID 的组合筛选。
- 插件筛选展示已安装插件的可读名称和稳定 `plugin_id`，卸载插件产生的历史日志仍可按保存的标识查询。
- 日志列表需显示时间、级别、模块/组件、消息和可展开的安全结构化字段；长消息和大量字段不得破坏页面性能。
- URL 查询参数可保存当前筛选条件，刷新或分享管理端链接时保持筛选；不得把敏感日志正文写入 URL。
- 页面提供加载、空结果、权限不足、日志降级、部分文件不可读和查询被限制等明确状态。

### 6. 审计与配置

- 运行日志配置变更本身写入审计日志，只记录变更字段和安全的新旧摘要，不记录敏感路径或内容。
- 运行日志查询不是审计事件；每次导出都写入审计日志，记录筛选摘要、结果数和输出大小，不记录日志正文。
- 管理员可在安全上下限内修改日志级别、单文件大小、分片数、保留天数和总容量；日志物理目录属于部署配置，不通过 Web UI 展示或修改。

## Acceptance Criteria

- [x] Server 正常启动后同时产生 stdout 和结构化本地运行日志，且默认日志目录被 Git 忽略。
- [x] 并发产生日志达到单文件阈值后自动切割，旧分片可被 gzip 解压读取，并按天数、数量、总容量三项限制清理最旧分片。
- [x] 模拟日志目录不可写、文件被 Windows 占用或磁盘写失败时，Server 不崩溃且 stdout 仍工作。
- [x] 管理员可在日志中心按时间、级别、模块、组件、插件、关键字及业务关联 ID 组合筛选运行日志。
- [x] 无 `logs.read` 的账户在导航、页面和 API 三层均无法访问运行日志；查询、导出、配置及审计日志权限互不隐含。
- [x] 已安装插件通过宿主 Logger 产生带正确 `plugin_id` 的日志，无法伪造其他插件标识；卸载后的历史日志仍可查询。
- [x] 自动化测试证明凭据、Cookie、Authorization、签名 URL、上游 CDN token、本地绝对路径和敏感请求正文不会进入文件、API 或导出内容。
- [x] 查询和导出 API 有时间范围、分页/结果数、关键字、扫描量和响应大小限制，并且不会暴露底层日志文件路径；导出操作留下脱敏审计事件。
- [x] 运行日志轮转清理不会删除或修改 SQLite 审计日志。
- [x] Web UI 在白色与深色主题下均可用，并覆盖加载、空状态、错误、受限和大结果集场景。
- [x] Server Go test/vet/build、Web UI test/typecheck/lint/build、权限生成漂移检查和 Windows 本地轮转烟测通过。

## Out of Scope

- 将运行日志上传到第三方 SaaS 或强制接入 ELK/Loki/OpenTelemetry Collector。
- 用运行日志替代持久任务状态、通知中心、指标监控或审计日志。
- 允许用户编辑、删除单条日志或通过 Web UI 浏览任意 Server 文件。
- 本任务内实现完整插件运行时；只定义并验证插件 Logger 与筛选契约。
- 默认实现实时日志 WebSocket/SSE 追尾；历史查询与刷新足以满足 MVP。

## Confirmed Product Decisions

- 使用推荐的默认保留策略：20 MiB / 10 个压缩分片 / 30 天 / 500 MiB 总上限，任一条件先触发即清理最旧分片。
- 日志策略允许管理员在安全范围内修改，日志物理目录只由部署环境控制。
- 运行日志和审计日志分域、分权、分开保留；插件日志属于运行日志，并使用宿主绑定的插件标识。
