# 统一媒体库扫描识别与目录对账

## Goal

让本地、115 以及未来 OpenList/Alist、CloudDrive2 等 provider 的既有媒体扫描，与 qBittorrent、115 离线下载等下载完成处理共用同一个 Profile 预处理、媒体类型解析、TMDB 匹配、分类和作品聚合核心。扫描器只建立只读文件事实，provider adapter 只列目录、接收事件或执行已授权的文件操作，不再各自猜测媒体身份。

## Background

- 当前 `medialibrary.ScanLocal`、`ScanProvider` 和本地事件处理会直接调用基础 `ParseMedia`，只使用媒体类型执行 Profile 分类，最终把所有条目写成 `unmatched`。
- 下载完成处理已经支持完整发行名、父目录、包名、Profile 有序识别预处理、TMDB 匹配和可信主媒体筛选，但入口仍位于 `DownloadWorker` 内，媒体库扫描无法复用。
- `MediaLibraryEntry` 是文件事实和目录展示的数据来源；媒体库更换 Storage、相对根或 115 provider root 时，旧条目和扫描记录已经要求事务内清空。
- 媒体库监听必须彼此独立并持续运行，不能占用下载、传输或上传的持久任务队列；TMDB 网络调用仍必须按媒体库配置限速并共享有界并发。

## Requirements

### R1. Provider-neutral 公共识别入口

1. 提取独立的公共媒体识别服务，接收 provider-neutral 的文件清单、包/目录提示、Profile 识别与分类配置、语言和地区，返回稳定的识别结果；下载完成和媒体库扫描都调用该入口。
2. Profile 有序识别预处理必须先于媒体类型、年份和标题候选解析；候选同时考虑主文件名、有意义父目录和包/目录名称，支持 `BDMV/STREAM/00000.m2ts` 回退到外层发行目录。
3. TMDB 匹配成功后再用完整元数据执行 Profile 分类；provider adapter、扫描器和监听器不得拥有私有标题清洗、TMDB 匹配或分类分支。
4. 下载完成时仍使用入队快照；既有媒体扫描使用媒体库当前 Profile revision。Profile 更新后重新识别扫描条目，但不得改变已经入队的下载任务。

### R2. 发现、分组与批量识别

1. 本地和云端扫描先只枚举受控根内的原始文件事实，再把文件按稳定识别单元分组后交给公共识别器；枚举阶段不得进行网络请求。
2. 电影发行目录、剧集作品/季目录和光盘结构必须形成合理识别单元。一个剧集季不得按每一集重复查询 TMDB；媒体库根目录下的多部独立电影也不得被错误合成一个包。
3. 同一轮扫描先按标准化候选去重；跨轮扫描通过源分组、文件指纹、Profile revision、语言和地区复用仍然有效的结果。正向缓存使用有界持久化，未匹配/网络失败使用更短的重试窗口。
4. 所有媒体库 supervisor 保持独立并行，不进入持久任务队列。TMDB 请求遵循每个媒体库的 `metadata_rate_per_second`、`metadata_concurrency`，并受进程级有界并发保护。

### R3. 持久化、作品身份与目录对账

1. 使用加法迁移保存每个媒体库识别单元的源身份、输入指纹、Profile revision、状态、TMDB 身份、置信度、分类结果、稳定错误码和人工覆盖状态；API 不暴露 provider 私有 ID、绝对路径或缓存内部键。
2. 匹配成功的电影和剧集使用 `media type + TMDB ID` 形成跨文件稳定作品键；未识别单元使用库内稳定 opaque 键，不得与已匹配作品误合并。
3. 文件条目继续作为 reconciliation 事实层，并关联对应识别单元。完整扫描删除已经证明消失的文件及孤立识别单元；`partial=true` 时保留未见旧数据。
4. provider 稳定 ID 移动/改名、本地创建/更新/移动/删除事件只重算受影响单元。定时增量和全量扫描继续作为一致性补漏。
5. 更换 Storage、相对根或 115 provider root 时，文件条目、识别单元、人工覆盖、扫描记录和 generations 在同一事务内清空；启用状态下自动建立新基线，旧目录作品不得残留。

### R4. 未识别、失败与人工修正

1. TMDB 未配置、认证失败、网络失败、无匹配、低置信度或标题不可解析时，文件事实扫描仍可成功并进入监听；对应识别单元以明确状态和稳定错误码进入“未识别”，不得伪装为已匹配。
2. 手动扫描和单项“重新识别”会绕过已到期或失败缓存重新计算，但不得重复枚举或修改源文件。
3. 管理员可以在未识别列表搜索 TMDB 候选、选择正确电影/剧集并保存人工匹配；服务端必须重新获取并验证该 TMDB 项目，再用当前 Profile 分类，不能信任客户端提交的标题、年份、分类或置信度。
4. 人工匹配按媒体库识别单元持久化，正常增量扫描保留；用户可以清除人工匹配并恢复自动识别。Profile 更新只重新分类人工匹配的可信 TMDB 元数据，不静默撤销人工选择。

### R5. API、目录 UI 与可观测性

1. 现有 `/entries`、`/catalog` 分页契约保持兼容，并增加安全的匹配状态筛选和必要的 TMDB/年份摘要；目录分组必须继续在 SQLite 中先完成再分页。
2. 媒体库详情的媒体清单提供“全部 / 已识别 / 未识别”切换；未识别项显示安全原因、相对来源摘要、重试、TMDB 搜索匹配和清除人工匹配操作。
3. 扫描记录补充已识别、未识别、缓存命中和识别失败统计；单个作品识别失败不把整个文件枚举标成失败，数据库或边界错误仍使扫描失败。
4. 新增稳定的 `media_recognition` / `媒体识别` operation。每批识别记录开始与唯一终态，包含 library/scan run、分组数、匹配/未识别/缓存命中数、耗时和稳定错误码；不按每个文件刷 info 日志。

### R6. 安全、兼容与只读保证

1. 扫描、自动识别、人工匹配和重试都只能读来源媒体；不得移动、重命名、复制、上传、删除或生成“未分类”目录。
2. TMDB 调用复用现有受控 HTTPS client、凭据优先级、API route 和脱敏规则。日志、审计、API、WebSocket 不得泄露 Cookie、TMDB 凭据、provider ID、完整云端路径或本地绝对路径。
3. 迁移升级后旧条目先作为待重新识别事实保留；后续 reconciliation 逐步生成新识别记录，不得把旧的基础文件名解析结果冒充 TMDB 已匹配。
4. 本地、115 和 fake provider 必须用同一组识别回归夹具；未来 provider 接入只实现扫描事实适配，不得复制识别代码。

### R7. 内置 TV / 动画预识别词包

1. Server 源码内置 MoviePilot-Help 的 `Words/TV.txt` 与 `Words/anime.txt` 固定快照，受保护默认 Profile 默认启用；运行时识别不得依赖 GitHub 联网下载。
2. 内置快照固定到 TV commit `f99c1b0bfd6721a727260e3e41e7d0bca73af8c7` 和 anime commit `8f26b5b48ac1a863cae97dd67689d05433394349`，保留原始 MIT LICENSE、来源 URL、commit 和同步日期，后续更新必须通过显式代码变更与回归测试。
3. 内置词包完整支持其实际使用的屏蔽、替换、替换后集数偏移、`EP` 算术、捕获组、前后查找以及 `{[tmdbid=...;type=...;s=...;e=...]}` 直接身份提示；不得把不兼容行静默忽略。
4. 内置词包先按 TV、anime 固定顺序执行，随后执行用户 Profile 的有序识别规则。内置规则不占用用户自定义规则的 64 条上限；复制 Profile 时保留词包启用状态，用户可以按 Profile 关闭某个只读内置词包但不能直接改写其内容。
5. 直接 TMDB 身份提示只作为受控识别输入，Server 仍向 TMDB 按指定类型/ID 读取并验证元数据，再执行当前 Profile 分类；不得信任词包中的标题、分类或远端响应缓存。
6. 支持回溯的兼容正则必须限制标题长度、单条匹配时间、回溯资源和应用次数。内置全部有效规则在测试期预编译；超时或运行错误以稳定识别错误进入日志/未识别状态，不能拖死扫描 supervisor。

## Acceptance Criteria

- [ ] 本地和 115 对同一真实发行目录生成相同标题、年份、媒体类型、TMDB ID、分类和作品键；完整七武士发行名以 `Seven Samurai + 1954` 查询。
- [ ] qBittorrent/115 下载完成与媒体库扫描通过同一个公共识别服务；测试能证明 provider adapter 中没有另一套标题/TMDB/分类逻辑。
- [ ] 一个包含多集的剧集目录只进行一次去重后的作品匹配，根目录下多部电影保持独立；BDMV 使用外层发行目录识别。
- [ ] TMDB 未配置、网络失败、无匹配和低置信度均保留文件事实并显示在未识别列表，媒体库仍能完成基线并进入监听。
- [ ] 单项重试能够重新识别；管理员搜索并确认 TMDB 候选后作品立即变为已识别、重新分类并按 TMDB ID 聚合，清除覆盖后恢复自动流程。
- [ ] 未变文件和未变 Profile 的重复增量扫描命中缓存且不重复请求 TMDB；Profile 更新会重新应用预处理/分类，人工匹配继续保留。
- [ ] 本地 watcher 和 115 生活事件只重算受影响识别单元；定时 reconciliation 能补齐丢失事件。
- [ ] 媒体库更换目录后，旧文件、旧作品、未识别记录和人工覆盖立即消失，新目录自动首次扫描，原目录文件没有任何变化。
- [ ] 完整扫描删除已证明消失的记录，partial 扫描保留未见旧数据；provider 稳定 ID 改名/移动不会制造重复作品。
- [ ] 目录 API 保持真实数据库分页，支持匹配状态筛选；UI 可在全部、已识别和未识别之间切换并完成修正操作。
- [ ] 日志中心可按“媒体识别”筛选批次开始/完成/失败，统计完整且不含绝对路径、provider ID、凭据或原始上游响应。
- [ ] 默认 Profile 在无用户规则时会依次应用内置 TV/anime 词包；两份固定快照的所有有效行均能解析、编译并按 MoviePilot 语义执行，直接 TMDB ID 和集数偏移有回归覆盖。
- [ ] 内置词包离线可用、带来源/commit/MIT 归属、可按 Profile 禁用且不可直接改写；复制 Profile 保留选择，用户规则始终在内置词包之后执行。
- [ ] 恶意或灾难性回溯输入在固定超时内失败并释放资源，不阻塞其他媒体库识别。
- [ ] v25 新装、v24 升级和重复迁移测试通过；Go/Web UI 全量质量门及 Windows 隔离脚本通过，测试后不遗留 Server 进程。

## Out of Scope

- 自动移动、重命名或整理既有媒体；手动文件整理仍属于未来文件管理页面。
- STRM 投影、signed 302、NFO/海报下载、Emby/Jellyfin/Player 刷新通知。
- Transmission adapter、OpenList/Alist 和 CloudDrive2 provider adapter 的具体接入；本任务只建立它们可复用的扫描/识别契约。
- 豆瓣、Bangumi 等多元数据源合并，以及跨媒体库共享人工覆盖。
- 真实 115 或真实媒体目录写入测试。

## Technical Notes

- 当前证据位置：`internal/medialibrary/scan.go` 在枚举时调用 `ParseMedia`；`internal/services/media_library.go` 对扫描文件只按 `MediaType` 分类并写入 `unmatched`；`internal/services/download.go` 与 `download_title.go` 持有完整 TMDB 识别流程。
- 新实现应把候选生成和 TMDB/classification orchestration 从 `DownloadWorker` 提取出来，再由下载 manifest 与扫描识别单元分别适配为公共输入。
- 不在数据库事务中执行 TMDB 网络调用。先持久化/读取文件事实与识别意图，在事务外完成受控匹配，再用短事务原子提交仍然属于同一 generation 的结果。
- MoviePilot-Help 仓库声明 MIT；两份词表合计 322 条有效规则，包含普通替换、38 条集数偏移、72 条直接 TMDB ID、45 条 lookbehind、107 条 lookahead 和 24 条 replacement backreference，不能用现有 Go RE2 数组直接承载。
