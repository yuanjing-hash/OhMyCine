# 优化媒体库入库与下载器逻辑

## Goal

把“资源来源、下载执行、115 收件箱、媒体识别、整理入库、媒体库对账、产物生成和媒体服务器刷新”收敛成一条用户可理解、可追踪、可恢复的流水线，减少重复配置和概念混淆，同时保留 PT、普通 BT、115 离线、115 分享转存、115 App 手工内容与自动追更的正确路由边界。

## Background

- 当前 Server 已实现持久化下载任务、完成清单复核、媒体识别、独立入库任务、媒体库增量对账、STRM/NFO/图片产物与 Emby/Jellyfin 刷新。
- 115 下载器绑定一个 115 Storage 和一个下载目录；普通离线、分享转存和 OhMyCine 任务均在该目录下使用独立 `omc-*` 子目录。
- 115 Downloader 级“自动监听生活事件”可接管用户在 115 App 中手工放入下载目录的普通目录，并跳过 `omc-*` 保留目录。
- 代码仍保留 MediaLibrary 级 `IngestEnabled/IngestDownloaderID/IngestProviderRootID` 旧摄取入口，与 Downloader 级生活事件入口并存。
- PT 资源不得交给 115 下载器；公开 BT、磁力和普通 HTTP(S) URL 可以交给 115 下载器。下载器只决定资源如何取得，不再限制最终媒体库介质。下载器产出数据源与目标媒体库属于同一数据源时保留 provider 原生入库路径；二者不是同一数据源时，才必须把来源完整物化到 Server 管理的本地暂存区，完成校验、识别、刮削、命名和冲突规划后，再入库到目标媒体库。部署方必须为跨数据源任务提供足够的本地暂存空间。
- 取消会先删除 provider 任务并保留文件，再停止下载、识别、入库和重试；删除历史默认删除 provider 任务与本地记录并保留文件，显式勾选才删除来源数据。

## Requirements

### R1. 统一概念边界

- Connection 只负责外部服务连接与凭据。
- Storage 只定义可访问的数据源根。
- Downloader 只负责接收资源、跟踪 provider 任务，并拥有其输入/下载目录。
- MediaLibrary 只定义最终媒体库根、识别命名、转移、冲突、STRM/元数据与刷新策略。
- Category/Profile 负责内容识别、分类、命名与目标规则，不把下载器目录伪装成媒体库配置。

### R2. 统一 115 摄取入口

- 115 Downloader 的下载目录是唯一输入收件箱。
- 普通离线下载、115 分享转存、115 App 手工放入的内容共享同一收件箱，但 OhMyCine 创建的 `omc-*` 目录由对应下载任务独占。
- Downloader 级“自动监听生活事件”负责手工内容摄取；媒体库不再要求额外的自动摄取目录。
- 每个 115 Connection 最多指定一个启用中的 115 MediaLibrary 作为“自动监听默认入库媒体库”；同一账号下所有启用生活事件监听的 Downloader 共用该目标。
- 默认入库设置只作用于 115 App 手工内容的生活事件接管；用户明确提交的离线下载、分享转存、站点下载和自动追更仍使用任务各自明确选择并固化的目标媒体库。
- 设置新默认库时必须在一个事务内替换同一 115 Connection 的旧默认，不允许短暂出现两个默认目标，也不能按媒体库排序静默兜底。
- 默认库必须启用、属于对应 115 Connection、具有有效 provider root，并使用云端移动或复制；本地库和不同账号的 115 库不能成为该默认目标。
- 修改默认库只影响之后接管的新内容；已经创建的 DownloadTask 保留原目标快照。
- 同一 provider item 无论被下载完成事件、生活事件或周期补偿扫描观察到多少次，只允许创建一条摄取/入库流水线。
- 迁移旧 MediaLibrary 摄取配置时不得丢失有效监听能力，也不得重复接管历史内容。

### R3. 保持来源与下载器兼容矩阵

- PT 站资源只允许进入支持 PT/做种的非网盘下载器。
- 公开 BT 站、磁力、普通 HTTP(S) URL 可以进入 115 原生离线或兼容的非网盘下载器。
- `.torrent` 文件不能直接提交给 115；公开 BT 站点在提交 115 前必须转换成 115 可接受的公开资源链接。
- 115 分享链接只允许由同账号 115 下载器接收。
- 来源与下载器的兼容规则不能被最终媒体库选择改变：PT 仍不得提交给 115 下载器；PT 由 qBittorrent 等下载完成后，可以选择 115 或其他网盘媒体库作为最终目标。
- 下载器和最终媒体库不再要求介质同类；创建任务时应根据“来源能力 + 下载器能力 + 来源后端 + 目标后端 + 可用 Transfer Executor”计算可选组合。
- 手工任务允许用户覆盖默认目标，并在提交时固化最终媒体库；“自动选择”必须来自明确的默认路由/分类规则，不能再按启用媒体库排序选择第一个兼容库。
- qBittorrent 等本地下载器的结果可以进入本地媒体库，也可以完成识别、命名和冲突规划后上传到 115 媒体库；做种所需源文件按做种策略保留，上传成功不能误删做种数据。
- 115 离线下载结果可以进入同账号 115 媒体库，也可以先从 115 拉取到 Server 管理的本地暂存空间，再整理到本地媒体库或上传到其他网盘媒体库。
- 115 分享转存和 115 App 手工内容仍以 115 为来源后端，但任务明确选择目标时可复用相同跨存储转移能力；生活事件手工内容仍使用该 115 Connection 唯一的默认入库库。

### R4. 一条可恢复的完成与入库链

- provider 报告完成后必须取得并持久化完整文件清单；同数据源任务可直接使用 provider 原生文件身份进入识别与规划，跨数据源任务必须先把来源完整物化到 Server 受管暂存区，再进行包选择、完整性校验、TMDB 身份和剧集季集复核。
- 未可靠识别、剧集集号不完整或清单不可信时不得部分自动入库；用户修正后应复用已完成文件继续。
- 入库任务必须使用创建时固化的目标媒体库、Storage、连接、命名、转移与冲突快照，避免运行中配置变化改变旧任务边界。
- 同一数据源内保留高效原生操作：同一本地数据源支持移动、复制、硬链接或软链接，同一 115 Connection 支持服务端移动/复制。跨数据源则统一以经过验证的本地暂存内容为中介：来源云盘先下载到暂存，目标网盘再从暂存上传，本地目标从暂存放置。
- 冲突策略支持询问、覆盖、跳过、重命名，并保持路径边界和 provider identity 校验。
- 入库成功后登记受管文件、推进媒体库变更版本，随后由增量对账生成/复用/清理 STRM、NFO、图片并触发 Emby/Jellyfin 刷新。

### R5. 自动追更复用同一流水线

- 订阅保存季、站点、下载器、目标媒体库、过滤条件、周期、每轮上限与优先级快照。
- 每轮先按媒体库覆盖率计算缺失集，排除已在下载或已入库的 claim，再搜索、过滤、选种并提交普通 DownloadTask。
- 订阅不得实现另一套下载或入库逻辑；下载完成后必须复用 R3/R4 的路由、识别、整理、产物与刷新流程。
- 同一订阅资源和剧集 claim 必须幂等，失败可释放或重试，入库完成后标记 imported。

### R6. 取消、删除与可观测性

- “取消”是停止整条流水线：先取消 provider 任务但保留文件，再取消仍在运行的下载、入库、做种和重试任务。
- “删除”只允许处理失败、已取消或完整收口的历史；默认删除 provider 任务与 OhMyCine 记录但保留文件，显式“完全删除”才删除来源数据。
- 115 删除文件使用回收站语义，不自动清空回收站。
- 下载、识别、整理、产物和刷新必须显示各自真实阶段、错误和重试状态，不能把“下载完成”误显示成“全部入库完成”。

### R7. 严格的可扩展执行契约

- 所有传统下载器必须通过统一的 Downloader Provider 契约和注册表接入；通用 Worker 不直接依赖 qBittorrent、115 等具体类型。
- Downloader 基础契约只包含所有 provider 必须具备的提交、查询、取消和健康能力；暂停/恢复、提前读取 metadata、完成清单、分类、做种、分享转存等通过能力声明和小接口扩展，不能要求不支持的 provider 实现伪方法。
- 插件在线媒体下载保持独立执行器，不属于本次传统下载器 Provider 抽象；本次不得为了统一外形而改变其插件权限、资产解析或 FFmpeg 合流路径。
- MediaLibrary 是保存最终媒体策略和状态的领域对象；不同本地/网盘数据源通过统一 Library Backend 契约提供规范化扫描、监听、文件身份、目录操作、导入和删除能力。
- MediaLibraryService 负责生命周期、识别、目录投影、变更版本和下游通知，不应在核心流程中不断判断 `local`、`pan115` 或未来 provider 类型。
- 入库必须由持久化的阶段编排器驱动：完成清单 → 路由 → 跨源物化（仅跨数据源）→ 校验/识别 → 规划 → 冲突处理 → Backend 执行 → 对账 → 产物 → 通知。每个阶段有清晰输入、输出、幂等键、恢复点和失败语义。
- provider 的差异只能存在于 Downloader Provider、Library Backend、Transfer Executor/Capability Adapter 内部，不能泄漏为贯穿多个 Service 的类型分支。

### R8. 跨存储 Transfer Executor

- Transfer 路由必须先比较下载器产出数据源身份与目标 Library Backend 数据源身份，而不是用 Downloader 类型推断目标是否兼容：身份相同选择原生同源执行器，身份不同选择“来源导出到本地暂存 → 目标导入”的跨源执行器。
- 数据源身份至少包含 backend/provider 类型和连接/账号 identity；115 同账号不同目录属于同一数据源，115 不同账号属于跨数据源。Server 可访问的本地 downloader 与本地媒体库属于同一 `server-local` 数据源；不同卷只影响 hardlink/move 等具体能力选择，不额外走云端式中转。所有判定都不能只比较展示名称。
- 首期矩阵至少覆盖：local → local 原生转移、115 同账号 → 115 服务端移动/复制、local → 115 上传、115 → local 下载后放置；未来 115 A → 115 B 或 cloud A → cloud B 复用“下载到受管暂存 + 上传”的跨源路径。
- 本地 PT 下载上传到 115 时，先基于完整 manifest 完成识别、目标命名和冲突规划，再上传到目标媒体库目录；上传成功后登记云端 provider identity，源文件是否保留由做种/清理策略决定。
- 115 离线结果进入同账号 115 媒体库时保留现有服务端移动/复制；进入本地、不同 115 账号或其他网盘时，才必须先完整下载到 Server 受管暂存区并通过 checkpoint。
- 跨存储任务应分别记录空间预检/预留、拉取或本地下载、完整性校验、识别刮削、规划、上传/放置、对账进度；任一步失败可从安全 checkpoint 恢复，不能产生重复上传或半成品被媒体库扫描接管。
- 现有全局“下载暂存目录”升级为 Server 统一受管工作根，不新增重复的中转目录设置；qBittorrent 任务和跨数据源物化分别使用其下的任务隔离子目录。仅跨数据源任务在创建/进入拉取阶段前按可得的资源大小和安全余量检查空间，空间不足时不得开始会继续占用空间的新拉取，并给出所需、可用空间和可清理任务。
- 暂存目录按任务隔离并记录所有权；只有任务拥有且不再被做种、重试、人工修正或其他流水线引用的内容才可自动清理。
- qBittorrent 等需要做种的本地来源在最终入库后继续保留暂存源，直至做种策略完成；本地目标优先使用不会破坏做种的硬链接或复制，不能为了释放暂存空间擅自停止做种。
- 取消默认停止后续阶段并清理仅由任务拥有的未完成临时文件，保留 provider 来源；删除与“完全删除”继续遵守 R6，不因跨存储而扩大删除范围。
- 目标后端尚未实现写入能力时，UI 应明确标为暂不支持，不能静默回退到别的媒体库或路径。

### R9. 固定的媒体类型一级目录

- 所有经过识别、Profile 分类和自动入库的媒体，不论来源是本地下载器、115 离线、115 分享、115 App 手工内容、插件下载、自动追更，目标是本地还是 115，以及使用同源还是跨源 Transfer Executor，目标目录都必须先按媒体类型分域，再进入对应类型内的自动分类。
- 电影一级目录固定为 `电影`，电视剧一级目录固定为 `电视剧`；这两个名称不是可编辑分类名，也不能由 provider、站点、下载器或用户模板改写。
- 目录顺序固定为 `媒体库根 / 电影或电视剧 / 类型内分类 / 作品目录 / 季目录`。电影分类只能落在 `电影` 下，剧集分类只能落在 `电视剧` 下；即使两类使用相同叶子分类名，也必须得到不同目标路径。
- Profile 的电影/剧集分类规则继续各自独立；目录模板只描述固定媒体类型根之后的结构。若历史模板已经显式以正确固定根开头，系统不得再次重复前缀。
- 已经排队的 DownloadTask/TransferTask 继续使用创建时冻结的完整模板快照，不因升级静默改道；数据库迁移只规范化 Profile 和 MediaLibrary 的未来任务模板，不改写任务快照或已入库文件。
- 手工重新整理使用当前 Profile/MediaLibrary 策略，也必须生成固定媒体类型一级目录；扫描、监听和对账本身仍只读，不得借分类迁移现有文件。

## Acceptance Criteria

- [ ] 配置和 UI 中不再存在与 Downloader 收件箱重复的 MediaLibrary 自动摄取目录入口；旧配置有明确、幂等的兼容/迁移行为。
- [ ] PT、公开 BT、磁力/URL、115 分享、115 手工内容的可选下载器和目标库均符合 R3，前后端使用同一权威矩阵。
- [ ] PT 资源不能提交给 115 下载器，但 qBittorrent 完成的 PT 内容可以选择 115 媒体库，完成识别/命名后上传且不破坏做种源文件。
- [ ] 115 离线内容可以选择本地媒体库，经过受管下载、校验、命名和放置后完成入库；选择其他已实现可写 Backend 时可继续上传到该目标。
- [ ] 同一 115 账号的下载目录到媒体库继续使用服务端移动/复制，不发生下载后重传；同一本地数据源继续使用既有本地转移策略。
- [ ] 只有数据源 identity 不同时才物化为按任务隔离、具有所有权记录的本地暂存内容；local → 115、115 → local 和未来 cloud A → cloud B 复用统一跨源执行器。
- [ ] Transfer Executor 通过来源/目标数据源 identity 和 capability 选择，不以 Downloader 类型硬编码拒绝跨介质目标。
- [ ] 跨存储传输在重启、网络中断、空间不足、上传返回不确定和用户取消后可安全恢复或收口，不重复上传、不把半成品暴露给媒体库扫描。
- [ ] 空间预检失败时任务不会开始新的下载或云端拉取；界面显示暂存根、预计需求、当前可用空间和阻塞原因。
- [ ] PT 做种任务入库到本地或网盘后仍可继续做种；清理器不会删除仍被 downloader 或恢复流程引用的暂存文件。
- [ ] 同一个 115 provider item 经下载完成、生活事件和补偿扫描同时触发时只产生一次入库。
- [ ] 同一个 115 Connection 最多存在一个自动监听默认入库媒体库；切换默认目标是事务性的，历史任务目标不变化。
- [ ] 没有有效默认目标时，生活事件监听不得回退到排序第一的媒体库，也不得接管后形成无目标任务。
- [ ] qBittorrent、本地入库、115 离线、115 分享转存、115 App 手工内容均能走完“清单复核 → 识别 → 整理 → 媒体库对账 → 产物 → 刷新”。
- [ ] 自动追更只下载确实缺失且未被 claim 的剧集，并复用普通下载/入库链。
- [ ] 取消和两种删除模式的 provider 任务、本地记录、来源文件、媒体库文件结果与界面文案一致。
- [ ] 任务重启、重复事件、接口超时和 provider 返回不确定结果不会造成重复下载、重复整理或越界删除。
- [ ] 新增一个下载器实现不需要修改通用 DownloadWorker 的 provider 类型分支；新增一个 Library Backend 不需要复制媒体库扫描、识别、目录和通知主流程。
- [ ] qBittorrent、115 Offline 等传统下载器通过统一 Provider 契约执行；插件在线媒体下载保持现状且回归测试不受影响。
- [ ] 入库每个阶段均可独立测试和从持久化 checkpoint 恢复，provider 实现不能跳过通用识别、所有权登记、对账和通知阶段。
- [ ] 所有新建的分类入库路线均生成 `电影/<电影分类>/...` 或 `电视剧/<剧集分类>/...`；本地、同账号 115、跨源上传/下载、插件下载、自动追更和手工重新整理共用同一目录规则。
- [ ] 相同叶子分类名在 movie/tv 下得到不同路径；电影分类不会落到 `电视剧`，剧集分类不会落到 `电影`，剧集路径在固定根和类型内分类之后仍保留作品与季目录。
- [ ] 历史任务模板快照不被迁移改写；已经显式包含正确固定根的 Profile/MediaLibrary 模板不会产生 `电影/电影` 或 `电视剧/电视剧`。
- [ ] 相关 Server 单元/集成测试、WebUI 类型检查与构建通过，关键迁移和兼容矩阵有回归测试。

## Out of Scope

- 新增 Transmission 或新的云盘 provider。
- 改变 Player 自身的数据源与播放架构。
- 重构 `PluginDownloadExecutor` 或把插件在线媒体下载并入传统下载器 Registry。
