# 插件平台与 Bilibili 在线媒体源

## Goal

建立 OhMyCine 面向非 PT 内容站点的安全插件平台，并以 Bilibili 作为首个真实插件验证完整体验：用户在 Server 安装和配置插件后，Player 能把该站点作为原生数据源使用，浏览站点主页、专区和个人内容，搜索、查看详情、播放视频，并按用户授权把指定推荐流参与 OhMyCine 总主页聚合。

该平台应让后续非 PT 站点通过稳定协议扩展，而不要求 Player 认识具体站点，也不允许第三方插件直接注入 Player 或 Server 管理端代码。

## Background

- PT 站点管理、聚合搜索、订阅和下载属于 Server 默认内建功能；PTTime 是未来第一个真实 PT 站点，不通过本插件平台接入。
- 插件平台主要扩展 Bilibili、YouTube、AcFun、直播或其他非 PT 内容站点，同时保留未来扩展元数据、通知、事件等能力的空间。
- Player 已有 `DataSource`、`ServerDataSource`、跨来源首页聚合、搜索聚合、身份合并与安全播放请求边界，应演进这些契约而不是建立第二套媒体系统。
- Server 已有 Player 设备令牌、媒体目录和播放入口、AES-GCM 凭据存储、任务队列、审计和支持 `plugin_id` 的结构化日志筛选基础。
- 当前 Hub 文档中的 Go 动态插件、插件自行注册 Gin 路由和任意 Vue UI 注入属于旧目标设计，需要被跨平台、隔离运行和声明式 UI 方案替代。

## Requirements

### R1. 产品与职责边界

- PT 站点保持 Server 内建，不作为社区插件安装。
- 非 PT 站点插件运行在 Server；Player 不下载、不安装、不执行插件包。
- 插件定义与用户创建的站点连接、账号凭据、在线媒体库实例分离。
- 在线站点库可在 Player 中与本地、115、Emby/Jellyfin 等数据源并列展示，但不能被误当成可扫描、移动、STRM 投影的物理媒体库。
- Player 在未连接 Server 或插件不可用时继续保持其它数据源可用。

### R2. 版本化插件协议

- 插件 Manifest 必须包含稳定 ID、版本、插件 API 版本、Server 兼容范围、能力、权限、配置 Schema、入口、作者、许可证、校验摘要和更新信息。
- 插件按能力组合，而不是只能选择一个固定插件类型。首期站点能力至少覆盖导航、内容流、搜索、详情、播放、刷新、个人内容和可选下载声明。
- 插件输出必须经过宿主运行时校验、限制大小并转换为标准 DTO；插件不能直接操作 Server 数据库、全局凭据、Gin 路由、Vue DOM 或 Player Pinia。
- 插件安装、启用、停用、升级、回滚和卸载具有明确生命周期、兼容性检查及失败状态。

### R3. 安全与可观测性

- 第三方插件默认不可信并隔离运行，不使用 Go `plugin` 作为默认正式运行时。
- 网络域名、凭据引用、插件私有存储、事件订阅、下载计划和文件能力均需显式权限；安装和升级前展示权限及权限变化。
- Cookie、Token 等站点凭据由 Server 加密保存，Player 永远不接收持久凭据。
- 插件只能使用宿主提供的受控 HTTP、日志、配置、缓存、凭据引用和事件能力；网络访问具有协议、域名、超时、重定向和响应体上限。
- 所有插件日志由宿主绑定 `plugin_id` 并统一脱敏；安装、启停、升级、回滚、删除和高风险动作进入审计日志。
- 默认不自动安装或自动升级插件。

### R4. 在线站点库与 Player 原生站点体验

- 一个插件连接可以发布一个或多个在线媒体库、个人集合和动态内容页。
- 插件可声明站点导航，例如推荐、热门、排行、影视、番剧、纪录片、收藏、稍后再看、历史和追更。
- Player 使用自身组件渲染 Hero、横向卡片、海报墙、视频列表、分页/游标、详情和操作，不渲染插件任意 HTML/JavaScript。
- 标准媒体项包含全局安全身份、来源、封面/背景、作者、时长、发布时间、统计、分集/分 P、合集、动态动作和播放能力。
- 插件可注册标准化站点动作；需要修改远端状态或产生任务的动作必须由 Player 明示，并由 Server 进行权限校验。

### R5. 主页贡献与刷新

- 插件可声明哪些内容流有资格参与 OhMyCine 总主页，不能强制占用主页。
- 用户可控制每个来源/内容流是否参与、顺序和显示位置；Player 保存设备侧展示偏好。
- Bilibili 默认仅以账号主页推荐流参与主聚合，收藏、历史和稍后再看默认不参与。
- 总主页顶部 Hero 可混合受信来源；下方栏目保持来源可辨识并显示来源标识。
- 支持刷新整个主页和单独刷新某个可刷新栏目；刷新创建新的推荐会话且不破坏正在浏览的旧游标。
- 单个插件超时或失败只影响其栏目，并显示来源级安全错误，不阻塞其它数据源。

### R6. 播放与交互契约

- Player 只向 Server 请求播放，Server 调用插件生成短时播放方案。
- 播放方案支持直链、HLS、DASH 音视频分离、多个可用清晰度、音轨、字幕、弹幕、必要请求头、过期时间及是否经过 Server 安全网关。
- 每个清晰度方案使用稳定的临时选择 ID，并提供安全展示字段，例如清晰度名称、分辨率、帧率、码率、编码、HDR/杜比标记和当前账号是否可用；Player 不根据站点私有字段猜测清晰度。
- Player 播放控制中提供“自动”及插件实际返回的可用清晰度，不能把账号无权播放或解析失败的档位伪装成可选项。
- 播放中切换清晰度时，Player 使用当前媒体身份和播放位置重新向 Server 请求对应方案；成功后尽量保持播放位置、暂停状态、音量、字幕/弹幕状态和播放进度同步上下文。
- 清晰度切换失败不得终止当前可用流；Player 显示来源级安全错误并保留或恢复切换前的播放方案。短时 URL 过期时由 Server/插件重新解析，不持久化旧地址。
- 持久 Cookie、Authorization、签名密钥和最终敏感上游地址不得进入普通媒体 DTO、缓存、路由、日志或播放历史。
- Player 使用现有 libmpv 播放链路，并继续遵守跨来源跳转时移除 Server Bearer 和私有请求头的规则。
- 站点播放进度、点赞、收藏、稍后再看、追更等交互作为独立能力声明；不支持的动作不显示。

### R7. 作品、分集、媒体版本与清晰度

- 整个 Server/Player 契约必须区分四层身份：作品、季/集、媒体版本和同一版本的流清晰度，不能把它们压成一个平面列表。
- 同一电影的剧场版、导演剪辑版、加长版、IMAX、不同片源/压制或不同存储来源属于同一作品下的不同媒体版本；只有可靠作品身份相同才允许聚合。
- 同一剧集先按季和集聚合，再在每一集下面保留多个媒体版本；同一集的 1080p、2160p、REMUX、不同来源不能显示成重复集数。
- Bilibili 的分 P/剧集属于内容分集；同一分 P 的 480p、1080p、4K 等属于同一媒体版本的清晰度方案，不得被误识别为不同版本。
- 媒体版本至少携带安全展示信息：版本/剪辑标识、分辨率、来源介质、REMUX/压制、HDR/Dolby Vision、视频/音频编码、音轨语言、发布组、大小、数据源和交付方式；缺失字段可为空但不能由 Player 猜测。
- Server 继续使用可靠 TMDB/提供方作品身份聚合作品，并使用稳定的分集身份和精确媒体版本身份防止误合并；标题和年份不能单独证明同一作品。
- Player 复用现有播放队列/选集弹层的交互和视觉组件作为“选集/版本”入口：剧集在这里选择集数并在同一集下选择版本，电影在这里直接选择版本；它不负责切换清晰度。
- PlayerControls 另设独立“清晰度”按钮，只展示并切换当前媒体版本的流分辨率/清晰度；不支持多清晰度或只有一个实际可用档位时按钮自动隐藏。
- 用户切换版本时尽量继承作品/分集播放进度；字幕、音轨和其它版本相关偏好必须按精确媒体版本重新校验，不能把不存在的轨道强行套用到新版本。
- 默认版本优先使用该作品/分集上次成功播放的版本；不可用时按用户播放偏好和当前实际可用性安全回退，不能选择无权限、失效或不可播放的版本。
- 入库命名、冲突检测、NFO/STRM 和 Player 展示均需保留版本信息；不同合法版本不能因为文件名模板或冲突策略被相互覆盖。

### R8. Bilibili 首个插件

- 支持安全登录和会话失效后的重新认证。
- 支持站点主页推荐刷新、热门/排行/专区、搜索、详情、分 P/剧集和 Player 播放。
- 支持收藏、稍后再看、历史、关注/追更等个人内容的浏览；远端写操作按插件能力和权限逐项开放。
- 使用 Bilibili 插件验证多页面导航、游标分页、短时播放解析、DASH、字幕/弹幕、主页贡献、来源故障隔离和插件日志。
- 首版包含真实视频下载：用户选择下载后进入 Server 持久任务队列，插件只生成受校验的下载方案，Server 下载视频/音频、校验并完成 DASH 音视频合流，再进入现有识别、整理和入库流程。
- 下载任务必须展示解析、视频下载、音频下载、合流、校验和入库阶段及可重试错误；取消和失败清理只能影响该任务受管的暂存产物。
- 下载使用用户发起任务时选择或按媒体库顺序解析出的目标媒体库、暂存目录、分类规则、命名模板、转移方式和冲突策略，不由插件自行决定最终文件位置。
- 下载清晰度只能从账号实际可用方案中选择；“自动”使用用户偏好内可成功获取的最佳方案，权限变化或地址失效时重新解析并安全降级或明确失败。
- 合流后的输出必须保留来源、清晰度和可用版本信息，避免覆盖同一作品/分集已经存在的其它合法版本。
- Bilibili 必须作为可独立安装、启停、升级和卸载的正式插件包实现，使用公开插件 SDK/插件库和相同 Manifest/权限/Host API；禁止在 Server 或 Player 中增加绕过插件协议的 Bilibili 专用适配分支。
- 不实现或协助绕过 DRM、付费权限、地区限制或站点访问控制。
- Player 的本地观看历史必须提供稳定分页，而不是只返回固定数量的“继续观看”；历史页可按来源区分本地记录与 Server 在线插件记录。
- 插件可声明 `playback.progress_sync` 和 `site.history`。Bilibili 支持时，Player 的开始、进度、暂停、停止和完成事件经 Server 回传 Bilibili；失败只记录来源级错误，不阻断本地历史保存和播放。
- Bilibili 历史读取使用站点游标/分页并映射为统一历史 DTO；本地历史与远端历史可以并列或去重展示，但不能用标题猜测同一条记录。
- 播放方案可携带由插件提供的弹幕轨道。Player 优先加载当前精确媒体版本的 Server 安全弹幕轨道，来源未提供时才回退到已有弹幕匹配渠道；插件 Cookie、上游地址和私有 Header 不得暴露给 Player。

### R9. Hub、SDK 与插件编写标准

- Hub 继续采用静态站点与 Registry/Release 分发，不成为运行时后台。
- 插件安装入口只存在于 Server 管理端；用户在插件页设置中添加 GitHub 插件仓库地址，Server 获取该仓库的标准 Registry 后展示、安装和更新插件，Player 不读取 GitHub 仓库。
- 一个 Server 可配置多个启用/停用、排序明确的 GitHub 插件仓库；仓库刷新失败按仓库隔离，保留上次成功且带时间标识的安全缓存，不影响已安装插件运行。
- GitHub 仓库标准借鉴 MoviePilot 的集中式插件索引与 Release 分发思路，但使用版本化 Registry、独立 Manifest、WASM 包、SHA-256、可选签名、权限差异和 Server 兼容范围，不能直接执行仓库源码。
- Server 必须把用户输入的 GitHub 仓库 URL 解析为固定 `github.com/{owner}/{repo}` 身份，通过受控 GitHub API 获取默认分支并将 Registry 固定到提交 SHA；拒绝任意 raw URL、凭据 URL、非 GitHub 主机和重定向到未授权主机。
- 发布插件需提供 Manifest、README、变更记录、权限说明、兼容矩阵、配置 Schema、源码/许可证、包摘要及签名信息。
- 提供官方 SDK、模板插件、协议 Schema、开发模式、校验/打包工具和兼容性测试套件。
- Hub 插件详情页显示能力、权限、兼容版本、校验状态、更新权限变化和安装入口。
- 插件包安装前完成格式、签名/摘要、兼容性、权限和危险内容检查；失败安装不得破坏正在运行的旧版本。

## Acceptance Criteria

- [ ] AC1: PT 管理在产品和代码边界上保持内建，插件清单不能注册成 PT 站点适配器。
- [ ] AC2: 一个模拟非 PT 插件可通过正式 Manifest 注册连接、在线媒体库、导航、内容流、详情和播放能力，Player 无需增加该插件专用分支。
- [ ] AC3: Player 能进入插件数据源，原生展示站点主页和多个专区，并在插件离线时保持其它数据源可用。
- [ ] AC4: Bilibili 推荐流可选择参与总主页；顶部 Hero 支持混合来源，下方栏目来源清晰，并可单独刷新 Bilibili 推荐。
- [ ] AC5: Bilibili 插件可以完成登录、推荐/专区/个人内容浏览、搜索、详情、分 P/剧集和真实 Player 播放。
- [ ] AC6: DASH 音视频、字幕/弹幕、多清晰度和临时播放凭据走标准播放方案；普通 API、日志和 Player 持久状态不泄露站点凭据或敏感上游 URL。
- [ ] AC7: 插件安装、权限确认、配置、启停、升级失败回滚和卸载均可在 Server 管理端完成并具有审计记录。
- [ ] AC8: 运行日志可按插件筛选，插件崩溃、超时或返回畸形数据不会使 Server 或 Player 主流程崩溃。
- [ ] AC9: Hub 文档、Manifest Schema、SDK 示例、打包校验和兼容性规范足以让第三方开发者实现第二个非 PT 站点插件。
- [ ] AC10: Windows 本地开发与运行不要求 Docker；Player、Server 与 Hub 的自动化测试覆盖主要跨层契约。
- [ ] AC11: Player 可在播放前或播放中选择“自动”或 Bilibili 当前账号实际可用的清晰度；成功切换尽量保持进度和播放状态，失败切换不会破坏原有可播放流。
- [ ] AC12: 同一电影的多个剪辑/片源/压制在一个作品详情下作为独立版本显示；同一剧集的一集有多个版本时只显示一次集数，并可从复用的选集菜单进入版本选择。
- [ ] AC13: Player 复用现有选集菜单选择集数或版本，并通过独立清晰度按钮切换当前版本的分辨率；无多清晰度时该按钮隐藏，切换版本仍继承作品/分集进度并重新校验字幕和音轨。
- [ ] AC14: Bilibili 首版可创建真实下载任务，展示解析、视频/音频下载、DASH 合流、校验和入库阶段，并将受管输出交给现有媒体整理流水线。
- [ ] AC15: 两个合法媒体版本经过下载、命名、入库、扫描、STRM/NFO 生成和 Player 展示后仍可区分，且不会因普通冲突处理互相覆盖。
- [ ] AC16: 官方 Bilibili 实现以插件库中的独立插件包运行；删除或停用该插件后核心 Server/Player 仍可运行，且核心代码没有 Bilibili API 专用分支。
- [ ] AC17: 管理员可在 Server 插件页添加 GitHub 仓库地址、刷新标准 Registry、查看来源与最近刷新状态，并从仓库卡片安装插件；错误仓库不会清空其它仓库或破坏已安装版本。
- [ ] AC18: Player 具有真正分页的观看历史；Bilibili 历史可分页读取，播放进度可按插件能力回传，回传失败不影响本地历史。
- [ ] AC19: Bilibili 播放时优先加载插件随播放方案返回的 Server 安全弹幕轨道，缺失时才回退旧渠道，任何持久状态和日志均不含站点凭据或上游敏感 URL。

## Out of Scope

- 本任务不接入 PTTime；PTTime 后续作为 Server 内建 PT 站点单独实施。
- 本任务不把 115、本地存储、Emby/Jellyfin 或下载器迁移为社区插件。
- 不允许插件直接注入任意 Server/Player JavaScript、直接注册管理 API 路由或读取宿主全局数据库。
- 不在首轮实现多用户跨设备首页偏好同步；Player 先保留设备侧聚合偏好。
- 不承诺完整复刻 Bilibili 官方客户端的全部社交、直播、创作和支付功能。
